# sys-zerotier — handoff

**Project:** a Nintendo Switch Atmosphère sysmodule that runs a ZeroTier node on the console
and bridges native LAN-play titles onto that virtual network, so LAN play works over the
internet from a single console with no PC helper.

**Program id:** `4200000000005A54` → `/atmosphere/contents/4200000000005A54/`
**Working tree:** `/home/lizzy/sys-zerotier` on the user's machine
(reachable from a cloud session as `$HOME/mnt/sys-zerotier` via `device_bash`).
**Target:** HOS 22.5.0, Atmosphère, Atmosphere-libs 1.11.2, devkitA64/libnx.

## Latest: 2026-08-30 LAN regression recovery

- The regression capture showed Splatoon 3's `2110-0101` was being generated by
  the compatibility shim reporting NIFM Error whenever ZeroTier's physical UDP
  wire socket was briefly paused. LAN state now follows the selected/requested
  virtual network once it has an assigned managed address; a transient uplink

- The bounded virtual-frame queue grew from 8 to 32 entries and the inbound
  datagram pool from 8 to 32 packets. The supplied status showed `nobuf 17`,
  proving that discovery bursts could exhaust the prior pool. The increase is
  approximately 110 KiB of fixed memory and does not change the ZeroTier arena.

## Latest: 2026-08-30 gamewide PIA host-identity normalization

- The new Mario Kart 8 Deluxe host trace rules out transport loss. The Switch
  receives every 873-byte browse request from `10.147.17.191:30000`, returns
  repeated 1361-byte unicast replies to that same managed endpoint, and VNet
  reports zero no-socket, no-buffer, checksum, or malformed drops. The reply
  is PIA 5.9 (`system version 5`, 1298-byte `LanSessionInfo`) and is being
  rejected by the browsing peer after delivery.
- The first browse-identity implementation guessed the host's PIA port by
  taking the first mirrored socket in `49152--49155`, then rewrote only values
  that exactly matched a physical-IP-derived guess. That is not a safe PIA
  identity model: `StationAddress` already carries the authoritative host port,
  and a title may have cached or constructed a stale value through a path that
  does not exactly equal the last NIFM result.
- Browse replies are now normalized from their declared PIA structure. For
  PIA 5.7--5.9, the managed address and advertised port are made consistent in
  `StationLocation`, network id, service-variable id, the 64-bit constant id,
  and the host `LanStationInfo` constant id. For PIA 5.10--5.45, only the
  documented IPv4 station address plus LAN-derived network/service ids are
  normalized; later-version constant ids are deliberately left untouched.
- The path no longer depends on first observing the physical NIFM address.
  Application data, variable ids, session-key parameters, and the appended
  crypto challenge reply remain byte-for-byte unchanged. The compact
  `browse id ... ip... p... net... c... n...` diagnostic records the original
  advertised identity, PIA crypto version/enabled flag, and number of changed
  fields for the next hardware proof.
- The Switch build succeeds and the ASan/UBSan VNet suite passes 76/76. The
  hardware-test archive is `dist/sys-zerotier.zip`, SHA-256
  `e0064e267ba74e8f89ef70570902b6e1e587b677cc7752d7f11865a592e26daf`.

  `SendTo` calls (`ZT only`), not `Connect`, `Send`, or `SendMMsg`.
- The path is healthy: ZeroTier remains online, the host transmits 137 game UDP
  packets, receives 17, and reports `nobuf 0`. The remote client therefore
  receives a reply but rejects its contents before presenting the room.
- PIA LAN 5.x derives multiple advertised identifiers from the host's local IP:
  StationAddress/StationLocation, network id, constant id, and service-variable
  id. An overlay IP header and NIFM result are not sufficient if PIA cached one
  of those values from the real interface through another identity path.

## Latest: 2026-08-30 Splatoon 2 overlay-only transmit correction

- Hardware disproved the prior PIA socket-lease hypothesis. In the failed run,
  sockets 49152, 40000, and 30000 remained open through discovery and the
  first 84-byte peer-session receive. PIA only released them after that packet;
  no close/reopen transition occurred for a lease to bridge.
- The lease experiment has therefore been removed completely. It was harmful:
  `status.txt` recorded `drops nobuf 17` because the retained, abandoned VNet
  queues continued receiving remote retries. `Close` and
  `ShutdownAllSockets` once again close their shadows immediately.
- The stronger failure mechanism is the duplicate transmit path. A successful
  VNet mirror was followed by the same managed-subnet destination being sent
  through the physical BSD/Wi-Fi socket. The physical interface has no route
  for the ZeroTier subnet and can report a delayed UDP ICMP/reset error on a
  later receive. PIA treats that unrelated physical error as a dead LAN peer,
  which matches the immediate socket teardown and `2618-0006`.
- A successful mirrored `SendTo`, connected `Send`, or `Write` is now a true
  interception: it reports the full payload length and does not leak a second
  copy onto physical Wi-Fi. Ordinary/unmirrored traffic still uses real BSD.
- Mirrored `Recv`, `Read`, and `RecvFrom` now translate physical-path UDP errors
  `ENETUNREACH`, `ENETRESET`, `ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, and
  `EHOSTUNREACH` to `EAGAIN`. This prevents a late physical-route error from
  destroying a healthy VNet PIA session. Rate-limited logs identify any such
  conversion as `physical errno ... -> EAGAIN`.
- Overlay receive diagnostics now include the first four payload bytes. This
  allows the next hardware log to distinguish browse, session, and gameplay
  packets without dumping full encrypted payloads.
- Hardware proof should show `ZT only` for outbound discovery/session packets,
  no `LAN lease`/`LAN reattach` lines, `drops nobuf` staying at zero, and
  `status.txt` `tx udp` increasing beyond the initial discovery packet.
- `make -j2 bundle` succeeds and the ASan/UBSan host VNet suite passes 76/76
  with leak detection disabled because LeakSanitizer cannot run under the
  desktop sandbox's ptrace environment. The hardware-test archive is
  `dist/sys-zerotier.zip`, SHA-256
  `7fd1996968da2fe98b75a7bd88c534a9bef8ee795b84edc70756bf98274dfe8e`.

## Latest: 2026-08-29 Splatoon 2 registration correction

- The Splatoon 2 US/CN crash capture is
  `logs and bin/01788050280_01003bc0000a0000.log`; the raw
  `01788050280_01003bc0000a0000_thread_info.bin` was parsed as DTI2 (27
  threads). The crashed `enl::TaskThread` deliberately aborts in
  `nn::socket::Initialize` after `nn::os::CreateTransferMemory` returns
  `0xD401`, `svc::ResultInvalidCurrentMemory`. The stack contains the matching
  0x5e0000-byte (6016 KiB) BSD work-buffer size. This is not an OOM result.
- `bsd.log` proves two complete command-0 registrations and teardowns, followed
  by the fatal before a third `RegisterClient`, `Socket`, or `Bind`. ZeroTier,
  NIFM, and the physical uplink were healthy. The failure is rapid reuse of the
  nnSdk socket work-buffer address while a retiring forwarded real-BSD session
  can still hold a copied TransferMemory handle.
- The first attempted correction translated command 0 to the handle-free HOS
  10+ `RegisterClientShared` command 33. Hardware disproved that approach: the
  IPC dispatch succeeded, but real BSD returned output `1`, which nnSdk rejects
  in `nn::socket::detail::InitializeCommon`. Command 33 is selected under
  different nnSdk service/option conditions and is not a transparent command-0
  replacement.
- `source/mitm/bsd_shim.cpp` therefore keeps ordinary command 0 for all three
  regional Splatoon 2 ids. It gives real BSD a sysmodule-owned proxy
  TransferMemory instead of forwarding the game's 6016 KiB region.
  The bounded real-BSD config preserves initial TCP and UDP sizes, removes TCP
  growth headroom, and lowers socket-buffer efficiency only as far as required
  to fit. The game's received TransferMemory copy remains managed and closes
  on handler return; real BSD never sees or locks those rapidly reused pages.
  MK8 and Splatoon 3 retain their proven registration paths.
- The first hardware run proved proxy registration, output `0`, and monitoring
  all succeed, but a second registration stopped inside the real-BSD dispatch
  when it reused the same proxy handle. The corrected low-memory design keeps
  the first registered real-BSD forward session alive for the game PID and
  answers later nnSdk command-0 cycles with that exact cached output. It never
  registers the TransferMemory object twice and uses one page-exact 592 KiB
  buffer rather than a multi-slot pool.
- The initially copied `report_00000000979e29d3.bin` was the older AFE2
  `nifm:u`/`FlushObservations` stack-overflow capture. The correct report is
  `report_0000000076b02baf.bin`: program `0100000000000034` (Atmosphere fatal),
  standard abort `0xFFE`, PC offset `0xAEF4`, with trace offsets `0xD370`,
  `0xAD00`, `0x19EA0`, and `0x20D08`.
- This was resolved against the exact fatal NSO extracted from the SD card's
  `stratosphere.romfs`, not against guessed symbols. Offset `0xAEF4` is the
  deliberate std-abort store to address 8. The caller path requests a 2 MiB

  the originating stop to the second proxy registration dispatch.
- Hardware proof should contain `RegisterClient PROXY`, then

## 0. 2026-08-28 transfer and latest crash diagnosis

### Decisive `0xD401` finding

- The latest Splatoon 3 report is
  `logs and bin/01787891759_0100c2500fc20000.log`, with a deliberate nnSdk
  User Break carrying result `0xD401 (2001-0106)` from `enl::TaskThread` at
  nnSdk build `[574284b4] + 0x17574c`.
- Atmosphere's creport reads the four-byte result at the User Break address and
  replaces its generic UserBreak result with that value. `0xD401` is therefore
  the exact result on which nnSdk aborted, not a generic fatal-report label.
- Atmosphere's SVC result definitions decode it as
  `svc::ResultInvalidCurrentMemory` (module 1, description 106). Ordinary SVC
  out-of-memory is description 104. The recurring Shoal failure is therefore
  **not an OOM crash**.
- The log sequence completes Splatoon's NIFM option/submit/state/result path,
  then dies before a second BSD `RegisterClient`. libnx creates and locks BSD
  transfer memory immediately before `RegisterClient`; Mesosphere returns
  `InvalidCurrentMemory` when that region cannot be locked in its current
  state. This explains why no second typed BSD call is logged.

### Lifecycle bug and implemented correction

- `source/mitm/bsd_shim.cpp` currently parks a registered BSD forward service
  in its destructor. This preserves the real `bsd:u` registration and its
  4.5 MiB transfer-memory reference after Splatoon tears down its first socket
  environment. The later BSD initialization then tries to create transfer
  memory over pages that are still retained/locked.
- `RegisterClient` also calls `tmem.Detach()`. The SF input `CopyHandle` is a
  managed copy, while synchronous forwarding gives the real BSD service its
  own copied handle. Detaching the MITM-side copy leaks another reference that
  can independently keep the transfer-memory object alive.
- The earlier handoff discussion that recommends parking registered services
  and detaching transfer memory is now superseded. Current `ryu_ldn_nx` parks
  only **unregistered** workaround sessions; registered sessions close
  normally. Our extension of that workaround is the important deviation.
- Implemented on 2026-08-29:
  1. park only unregistered/dummy forward sessions;
  2. allow registered forwarding sessions to close normally;
  3. remove `tmem.Detach()` after synchronous `RegisterClient` forwarding; and
  4. log registered-session and transfer-memory release.
- Expected proof on hardware: the first registered BSD session logs a normal
  release instead of `parked`, and the Shoal reinitialization reaches a second
  `RegisterClient ENTER` without `0xD401`.

### Frozen source warning

- On 2026-08-29 the BSD lifecycle correction above was applied: registered
  sessions now close normally, `RegisterClient` keeps its received CopyHandle
  managed, and only unregistered workaround sessions are parked. The frozen
  synthetic CreateRequest experiment was removed; Splatoon's local proxy once
  again retains a real Nintendo IRequest underneath its Ryujinx-facing
  state/events compatibility surface.
- The new lifecycle trace emits `registered ... releasing bsd/tmem`, followed
  by `released bsd/tmem`. A later `RegisterClient ENTER` is the decisive
  hardware proof that the old transfer-memory state no longer blocks reinit.
- `make -j2` completed on 2026-08-29 and the host VNet suite passes 76 checks
  with zero failures under ASan/UBSan. `make bundle` produced the hardware-test
  package `dist/sys-zerotier.zip` (SHA-256
  `5ae4c578ae73918e73fc2ad8b7d51065592b2ac77b5ef827276d3f653cca2a99`).
- The first post-fix multi-title run exposed an independent MK8 regression:
  BSD process teardown did not necessarily send command 26 for each socket, so
  the fixed eight-entry `(pid, fd) -> VNet fd` table retained shadows belonging
  to old PIDs. On the third MK8 launch only UDP 49152 and 40000 received
  mirrors; UDP 30000 did not, while orphaned receive queues exhausted VNet's
  eight-packet pool (`drops nobuf 203`). The current source now closes every
  shadow belonging to a PID when its registered BSD object is destroyed and
  after successful `ShutdownAllSockets`, without allocating or nesting the BSD
  table lock with Port's VNet lock. Expected teardown proof is
  `releasing bsd/tmem shadows N`; the next launch must show mirrors for all
  three MK8 sockets and `nobuf` should remain zero during discovery.
- The full direct DTI2/parser evidence is retained in `logs and bin/` and
  `tools/parse_dti2.py`. The multi-gigabyte `.research-splatoon/` cache is not
  required to continue development and is intentionally excluded from the

## 3. What their code says that ours got wrong

Ranked by how likely each is to be *the* bug.

### 3.1 `MaxDomains = 0` — most likely cause (FIXED this session)

Our `MitmServerOptions` inherited `MaxDomains` and `MaxDomainObjects` from
`DefaultServerManagerOptions`, which are **0 and 0**
(`Atmosphere-libs/.../sf_hipc_server_manager.hpp:24-30`).

A HIPC client may send `ConvertCurrentObjectToDomain` — a **control** request, answered by
the framework, never by one of our handlers — before it sends any service command. With
`MaxDomains = 0` that conversion fails inside libstratosphere, the client takes the error
inside its service-creation path, and dies. That is precisely "sessions accepted, no handler
reached, abort in `CreateClientServiceByHipc`".

ryu_ldn_nx uses `0x10` / `0x100` (`sysmodule/source/main.cpp:175-181`). **Now changed to
match.** Watch `.bss`: domains are not free and our arena low-water was already 278 KB.

### 3.2 The dummy first session must not be intercepted (FIXED this session)

`bsd_mitm_service.cpp:303-322`:

> Skip the first BSD session from each game process. Games typically open a "dummy" first
> session that is never used (no RegisterClient is ever called on it). Intercepting this
> session causes system instability/crashes even if we try to handle it gracefully. The
> actual networking happens on session #2+.

Our `bsd.log` shows exactly two accepts and no `RegisterClient` — consistent with this.
`ShouldMitm` now counts sessions per pid and returns `false` for #1.

### 3.3 Closing an unregistered forward session freezes the system (FIXED this session)

`bsd_mitm_service.cpp:118-127` and `:237-252`. A `BsdMitmService` destroyed without ever
having received `RegisterClient` must **not** let its forward `Service` close. They park the
`shared_ptr` in a static vector forever. We now do the same, gated on `m_registered`, with a
`CleanupAbandonedServices()` for a future safe drain point (they call theirs on LDN
disconnect; we have no equivalent moment yet, so nothing calls it).

### 3.4 `transfer_memory.Detach()` — RESOLVED 2026-08-29

`bsd_mitm_service.cpp:437-443`:

> CRITICAL: Detach the handle to prevent `sf::CopyHandle` destructor from closing it. …
> Since we're a MITM proxy, we must NOT close handles that belong to the client process —
> we only forward them.

The later `0xD401` investigation resolved the ambiguity. HIPC gives the MITM process a
managed copy of the client's handle, and synchronous forwarding gives real `bsd:u` another
copy. Detaching our received copy leaks a reference to the same transfer-memory object.
Combined with parking the registered forward service, that can keep the socket-pool pages
locked across Splatoon's BSD teardown/reinitialization and make the next
`CreateTransferMemory` return `InvalidCurrentMemory`.

The 2026-08-29 build therefore leaves the input `sf::CopyHandle` managed and closes
registered services normally. Only unregistered workaround sessions remain parked. This
supersedes the quoted ryu_ldn_nx recommendation above; the next hardware run is the proof.

### 3.5 Command-table deltas — STILL OPEN

Ours declares 0–27, 29, 30, 33, 36 (32 commands). Theirs declares 0–33 with firmware gating.
Concrete differences to reconcile against `ibsd_mitm_service.hpp`:

- **Command 36 is ours alone and speculative.** We invented `RegisterClientVersion` from a
  switchbrew line. If a game calls 36 and our signature is wrong, `sf` rejects the request
  before the handler runs and nothing logs — the exact shape of the current failure.
  **Delete it unless it can be justified**, or at minimum gate it behind a config flag.
- **Missing 28 / 31 / 32**: `GetResourceStatistics`, `EventFd`, `RegisterResourceStatisticsName`.
  `EventFd` (31) matters later — it is the only way to wake a forwarded `select()` from our
  own RX thread (see §5).
- **Buffer *types* differ.** They use plain `sf::InBuffer` / `sf::OutBuffer` (not
  AutoSelect) on cmd 4 `Open`, cmd 7 `Sysctl`, cmd 28 `GetResourceStatistics`, cmd 32 name.
  A type mismatch is another silent pre-dispatch rejection.
- **Cmd 29 `RecvMMsg` argument types differ.** Theirs is `s32 fd, s32 vlen, s32 flags,
  s32 timeout`; ours has `u32 vlen, u32 flags, **u64 timeout**`. `sf` sorts InData by
  alignment ascending, so a `u64` there **moves the whole raw layout** and the request size
  will not match. Fix to all-`s32`.
- Add the version gates they use: 29/30 `hos::Version_3_0_0`, 31 `Version_7_0_0`,
  32 `Version_15_0_0`, 33 `Version_10_0_0`.

### 3.6 Confirmed correct in ours — do not "fix" these

- `RegisterClient` input layout. Their header states the rule: *"sf sorts InData by
  alignment (ascending). LibraryConfigData align=4 comes first, then ClientProcessId and
  tmem_size both align=8 in declaration order. This matches libnx layout."* Our
  `BsdServiceConfig`(32) + `ClientProcessId` + `u64 tmem_size` is right.
- `RegisterClient` output is `Out<u64>`, not an errno pair. Ours is right.
- `.in_send_pid = true` **plus** `.override_pid = client pid` on the register commands.
  Without the override the real `bsd:u` registers *our* pid and every later fd lookup fails.
  Ours is right. Note they do **not** pass `.override_pid` on ordinary commands; we do — this
  is harmless but worth an experiment if problems persist.

### 3.7 Sizing and structure differences worth adopting

| Thing | ryu_ldn_nx | ours | note |
|---|---|---|---|
| `MaxSessions` | 16 | 8 → **16** | changed this session |
| `PointerBufferSize` | 0x1000 | 0x1000 | already matching, confirmed exact on hardware |
| server threads | 2 (1 + 1 extra), 32 KB stacks | 1 | **still open** — one thread means a blocking forward stalls everything |
| own socket sessions | `num_bsd_sessions = 14`, `bsd:s` not `bsd:u` | check ours | 14 is `ConcurrencyLimitMax`; the default 3 saturates and returns errno 113 instead of blocking |
| heap | 384 KB ExpHeap + 1 MB malloc | 1024 KB arena | ours is tighter; `arena: 278 KB free (low-water)` has **zero margin** |

   `sys-zerotier.nso` were rebuilt successfully on 2026-08-25. Host VNet tests
   pass (74 checks, 0 failures). The next hardware run should specifically

   13-packet failure point.

6. Receive-path checkpoint: `RecvFrom` now drains a queued VNet datagram for
   an observed shadow socket and returns a network-order BSD `sockaddr_in`.
   `Select` and `Poll` report already-queued virtual data as readable; empty
   queues continue unchanged to real `bsd:u`. VNet broadcasts fan out to all
   matching bound sockets. This is built and host-tested (76 checks, 0
   failures), but does not yet use an EventFd to wake a real blocking select,
   so remote arrival can be delayed until the game next polls/times out.

**Known wart in what I wrote:** the per-pid slot is claimed on the dummy session's `+1` and
that increment is never matched by a destructor call (we never construct an object for it),
so a slot stays claimed for the lifetime of the game process. With 4 slots, four successive
different games fill the table and the fifth is refused. ryu_ldn_nx has the same asymmetry
and lives with it. If it matters, reap slots whose pid no longer exists.

## 5. The architecture study — what to build next

A subagent read their entire data plane. The findings that will save the most time:

- **They never fabricate a file descriptor.** Every `Socket()` is forwarded to the real
  `bsd:u` and the real fd is returned verbatim; the proxy is a shadow object keyed on that
  fd (`proxy_socket_manager.hpp:585`). Consequence: every proxied socket burns a real kernel
  socket, and **`Accept` cannot be proxied at all** — they quietly gave up on it. Decide the
  accept story before writing code.
- **The "is this ours" predicate is address-based only**, evaluated at Bind/Connect/SendTo:
  `10.114.0.0/16` for them (`bsd_types.hpp:49-63`). Bind additionally captures `INADDR_ANY`
  and then *also* forwards the real bind so non-LDN traffic still works. For us the
  predicate is the ZeroTier subnet plus `INADDR_ANY`.
- **Their blocking `recv` is an untimed `Wait()` on a 2-thread IPC server.** Two concurrent
  blocking recvs park both threads and the whole MITM stops answering — including the
  `Close` that would release them. Bound the wait or return `EAGAIN` and let the game's poll
  loop drive. They accept and silently discard `SO_RCVTIMEO`.
- **`select`/`poll` never block on proxy fds** and unconditionally report writable, so the
  game busy-spins. On mixed real+proxy sets they forward to the real `select` with the game's
  timeout, so a packet arriving 1 ms into a 500 ms wait is invisible for 499 ms. The fix is
  to inject a `bsd:u` `EventFd` (cmd 31) into the forwarded set and signal it from the RX
  thread — which is why declaring cmd 31 matters.
- **Two latent self-deadlocks on their non-recursive manager mutex**
  (`proxy_socket_manager.cpp:333` and `:89`), unreachable today only because their TCP path
  is dead. Our ZeroTier backend *will* reach them. Copy their good pattern — copy the
  callback out under the lock, invoke it unlocked — everywhere, not just in `SendProxyData`.
- **`GetProxySocket` returns a raw pointer after dropping the lock**, and a blocking `recv`
  can outlive the object. Use `shared_ptr` from the lookup.
- **Key the socket table on `(pid, fd)`, not bare `fd`.** Theirs is a process-global map
  keyed on fd alone; it survives only because one whitelisted game runs at a time.
- **Alignment.** IPC buffer pointers are not aligned and their `SockAddrIn` is packed;
  `__builtin_bswap32` through such a pointer **data-aborts on ARM64**. Always `memcpy` into
  an aligned stack copy first (`bsd_mitm_service.cpp:1059-1064`, and three more sites).
- **Byte order.** Theirs is genuinely inconsistent — `GetSockName` and `RecvFrom` hand the
  game `sin_addr` in opposite orders. Pick network order at the BSD boundary and convert
  once at the wire boundary. `sin_len` must be 16 or the game rejects the address.
- **Broadcast must fan out to every matching socket**, not the first. Single delivery broke
  PIA's mesh protocol in Smash.
- Bounded rings, drop-oldest, 32 × 2000 B per socket ≈ 64 KB — against our much smaller
  budget that is far too big. Size the ring against our arena, and **count drops**.

Our own `source/net/vnet.cpp` (ARP/IPv4/UDP/ICMP, 74 passing host tests) is the backend that
replaces their Ryujinx relay. The port is: keep their *session and forwarding* layer, replace
their *data plane* with `VNet`, and fix the flaws listed above rather than inheriting them.

Threading note that still applies: MITM handlers run on the server-manager thread while the
node thread may be inside `VNet::onFrame`. `VNet` needs locking before interception is
switched on.
